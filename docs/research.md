# Phase 1 research

## Platform findings

- **iPhone.** Core Bluetooth supports central and peripheral roles. The central can scan for advertised service UUIDs, connect, discover services and characteristics, and perform GATT writes and reads. iOS requires a Bluetooth usage description and user authorization. Core Bluetooth exposes a local peripheral identifier, so the scanner cannot show a peer MAC address. [Core Bluetooth](https://developer.apple.com/documentation/corebluetooth) · [Bluetooth usage description](https://developer.apple.com/documentation/bundleresources/information-property-list/nsbluetoothalwaysusagedescription)
- **GATT.** Use one custom primary service with separate write and read characteristics. At the default 23-byte ATT MTU, a write request carries at most 20 value bytes. A request acknowledged before the response is read avoids subscription setup and MTU negotiation in the first hardware test. [Bluetooth Core Specification, Vol 3 Parts F and G](https://www.bluetooth.com/specifications/specs/core-specification/)
- **Wear OS.** Android exposes GATT server and LE advertiser APIs. Availability varies by Bluetooth adapter and firmware, so check advertiser capability and report both synchronous and asynchronous failures. Wait for a successful service registration callback before advertising. Android 12 and later require Nearby Devices runtime grants for advertising and connecting. Google Play services' Wearable Data Layer targets paired Android handhelds and is outside this transport. [GATT server](https://developer.android.com/reference/android/bluetooth/BluetoothGattServer) · [LE advertiser](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeAdvertiser) · [Permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) · [Wearable Data Layer](https://developer.android.com/training/wearables/data/overview)
- **Background behavior.** Apple's Bluetooth background modes can wake apps for specific BLE events. Background scan behavior differs from foreground scanning. State restoration is opt-in via a restoration identifier and requires restoration callback handling. It is separate from reconnect policy. This first test uses a foreground session. In a role-reversed experiment, start with both apps in the foreground because iOS background peripheral advertisements can move service UUIDs into an overflow area with restricted discovery. [Core Bluetooth background processing](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html)
- **Notifications.** ANCS is an Apple system GATT service. An accessory acting as GATT client can subscribe and request attributes subject to system authorization. A companion iPhone app cannot use UserNotifications to read other apps' notifications. ANCS availability, authorization, actions and persistence require a separate hardware investigation. [ANCS specification](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleNotificationCenterServiceSpecification/Introduction/Introduction.html) · [UserNotifications](https://developer.apple.com/documentation/usernotifications)
- **Provisioning and authentication.** Samsung documents initial setup for Galaxy Watch4 and later through Galaxy Wearable on a compatible phone, subject to model-specific standalone options. The source review found no public iOS path for Samsung account enrollment, device provisioning, or OEM companion authentication. Custom GATT, Bluetooth bonding, and OEM setup are separate operations. Use a watch already set up through a supported route, with developer installation enabled. [Samsung setup and compatibility](https://www.samsung.com/ca/support/mobile-devices/set-up-your-galaxy-watch-with-or-without-a-phone/)

## Open hardware questions

1. Which Galaxy Watch models and firmware versions expose connectable peripheral advertising while their official Android companion remains configured?
2. Does the iPhone see the custom UUID consistently, and can it rediscover the watch after disconnect, Bluetooth toggles, or foreground changes?
3. If peripheral advertising fails, record the watch model, firmware, adapter capability and callback/error code. Then test an iPhone foreground GATT peripheral with a Wear OS central using a service UUID scan. Keep the same frame contract and record whether foreground discovery, exchange and later background discovery work independently.
4. Which link security and explicit user verification can be enforced across models before introducing any personal data?
